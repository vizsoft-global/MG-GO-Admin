1. What the client requested

  1. Empty a whole module in one operation instead of ticking rows, gated by its own permission — never implied by Edit or Delete.
  2. No silent grant: shipping must not hand the capability to anyone who already exists.
  3. A count before the act, and a typed confirmation — never a single click.
  4. Cover the modules: drivers, deliveries, requests, visits, earnings, attendance, vehicles, assets, fuel, zones, partners, companies, rules, notifications, e-signature, wrong actions, reconciliation, verifications, payroll.
  5. Clean the files too, not just the rows.
  6. Vehicles: one identity (plate, not a second “bike ID”), counts on the list, a real detail page, assign a rider from the fleet side, see and assign the rider’s assets.
  7. Riders should see their own vehicle’s handover / accident / document / service / asset history in the app, read-only, without exposing paperwork.

3. Permission model — the exact gate

  • Matrix wording: View data · Add data · Edit data · Delete individual records · Bulk delete / Clear all data.
  • Who may clear: super admin; a Manager (access_kind = 'manager', full catalogue); a User holding that module’s individual tick; or a non-custom role that carries the slug. Enforced in the database by _admin_purge_require(slug) via _admin_purge_slug_for_entity(entity).
  • Page access: the route requires data.cleanup. That slug is granted automatically to anyone holding a bulk-delete tick, so a User lands on Clear all rather than on a tab whose every request would be refused. The row-by-row candidate tabs and their storage sweeps remain super admin.
  • Not aliased: holding {module}.manage, .create, .edit or .delete clears nothing.

3.1 Read-only SQL proof (safe to run on production)

select (select count(*) from admin_permissions
         where slug like '%.bulk_delete')            as catalog_rows,   -- expect 22
       (select count(*) from admin_role_permissions
         where permission_slug like '%.bulk_delete')  as role_grants,     -- expect 0
       (select count(*) from admin_user_permissions
         where permission_slug like '%.bulk_delete')  as user_ticks,      -- expect 0
       (select count(*) from admin_permissions
         where slug = 'data.cleanup')                 as data_cleanup;    -- expect 1

Blocker codes the preview can return, and their client copy: blocked_by_deliveries → “Deliveries still point at these rows.” · blocked_by_restaurants → “Restaurants still point at these rows.” · blocked_by_fuel → “Fuel log rows still point at these vehicles.”

admin_purge_run_all(entity, limit) clamps the batch to 500 rows; the server action loops batches inside a time budget and reports how many are left if it stops early.

QA data-destruction rules. Never run Clear all on production Drivers or Deliveries during testing — that removes real riders and real orders. Use driver_groups or order_recon for a genuine run, and use the preview-only path (count + blockers) for the rest. A clear is permanent.

5. Verify — Admin

A. Staff Access matrix

  • Super admin → /en/settings/staff-access. The module matrix has a fifth column Bulk delete / Clear all data.
  • Every existing user shows that column unticked (0 grants at ship).
  • Tick Bulk delete for one module on the test User and save. Re-open: the tick persisted; no other module’s tick changed.
  • On the same user, tick Delete individual records only. The bulk-delete column must stay unticked — Delete must not carry it.
  • Untick the bulk-delete tick again and confirm the User loses the Clear all surface (section E).

B. Where the control appears

  • Sidebar → Settings → Data cleanup is visible to super admin and to a bulk-delete holder, and hidden from a User with none.
  • The page opens on the Clear all data tab for a bulk-delete-only User (no row-by-row tabs drawn).
  • As super admin, the row-by-row candidate tabs are still present and still work.
  • List-page Clear all buttons exist (destructive + trash icon, visually distinct from Add) on the 14 list pages that have one: drivers, deliveries, requests, visits, zones, partners, assets, fuel, notifications, document expiry, delivery rules, incentive rules, wrong actions, order reconciliation — and are absent when the tick is missing.

C. Preview — count and blockers

  • Open Clear all on Driver groups: the button shows a live row count (“N rows”); the dialog title reads “Clear driver groups”.
  • Open Clear all on Zones while drivers still reference zones: the primary button is disabled and the reason names deliveries/restaurants/fuel as applicable.
  • Repeat after clearing drivers (step D): the block lifts.
  • Confirm the count is the whole module, not selected rows — the banner says so.

D. The run itself

  • Trigger Clear all on Driver groups. The typed phrase is required (for example CLEAR 3 DRIVER GROUPS); any other text leaves the confirm disabled.
  • Confirm → success toast names the module and the number cleared; the list is empty afterwards.
  • Run it a second time → it finds nothing left (idempotent, no error).
  • If you stop it early (a large module), the toast reports rows cleared and rows remaining, and running again continues.
  • Buttons are disabled while the run is in flight (no double submit).

E. Access refusal, both layers

  • As the User with no bulk-delete tick: the Clear all control is not drawn anywhere.
  • Call it directly (devtools → invoke the server action or POST the RPC): it is refused, not silently ignored.
  • As a rider session (set local role authenticated): not_authorized, as in §3.2.
  • As a User holding only {module}.bulk_delete for one module: clearing a different module is refused.

F. Storage and linked logins

  • Clear a module that had attachments (safe candidate: a driver group is not enough — use order reconciliation or a small request set you created for QA).
  • The storage objects for those rows are gone afterwards, not orphaned.
  • Clearing Drivers (only with approval) removes the linked rider app logins, and those riders can no longer sign in with their old passcode.

G. Preserved data

  • After every test run above: app_settings, roles, locales, menu layouts and staff profiles are untouched.
  • The two system companies (MG / Unassigned) survive a Companies clear.
  • Audit log (/en/settings/logs) has one entry per clear, with the entity and count.

H. Vehicles — list

  • /en/vehicles shows the KPI strip: Total, Unassigned, Bike, Car, Active, Replacement.
  • Each tile equals the row count of the list after clicking it; Unassigned shows only vehicles with no rider; Bike/Car match the kind dropdown.
  • Clicking Total clears the KPI-driven filters.
  • No vehicle can be identified by a “bike ID” anywhere a plate should appear.

I. Vehicles — detail and assignment

  • Open a vehicle: plate is the ID badge, with Kind / Condition / Status / On Duty badges beside it.
  • The field grid is six across on a laptop and carries Chassis, Model, Year, Kind, Car type, Type of use, Fuel, Chip, Limit, Location, Owner, Replacement, Driver, MG ID, Phone, Project.
  • Assign driver searches by name, MG ID or driver code (recents appear first, the trigger never shows a raw UUID). Saving shows “Driver assignment saved” and the Driver / MG ID / Phone rows update.
  • Assign rider B to a vehicle that already had rider A: A is unassigned (their vehicle_id is cleared), and the vehicle shows B.
  • Unassign: the vehicle becomes Unassigned on the list and the KPI count moves.
  • Edit form also offers the driver picker and saves without touching the assignment unexpectedly.

J. Vehicles — assets, and the Assets module

  • Vehicle → Assets tab lists the assigned rider’s assets (empty state when none, with the prompt to assign a driver first).
  • Assign opens a catalogue search, requires a quantity, respects the stock gate, and the row appears after saving.
  • Add asset opens the asset sheet (needs assets.create).
  • /en/assets → Assignments tab now has its own Add (previously only the catalogue tab had one).
  • Assets actions are refused for a user without assets.manage / assets.create.

K. Companies popup

  • /en/settings/source-companies → Edit: wide dialog (~96vw, ~95dvh on a laptop), two columns — fields left, live preview right.
  • Actions sit in the footer (left title/subtitle, right Cancel + primary); the Close X is outside the frame top-right.
  • No inner scrollbar at 1366×768.
