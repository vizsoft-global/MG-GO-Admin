1. What the client requested

  • Move payroll from one hard-coded classification to a client-owned rules engine (MGGO Payroll SOP v4.0).
  • Per client: hour values (full / half / reduced), required hours per day, a default day status, and Good / Average thresholds.
  • Per client and per month: an ordered rule list matching on zone band, zone name, orders and worked hours; first match wins.
  • The SOP result codes: 12 full day · 3h reduced · HALF half · ACT actual · ABS absent · ALH absent LH · ALO absent LO · CUS custom.
  • Fixed precedence: manual adjustment > Operations > first matching rule > client default > legacy fallback.
  • Zone efficiency from the previous completed month only: DPD = orders ÷ rider-days, target DPD = the average across active zones, efficiency = DPD ÷ target × 100, banded Good ≥ 110 / Average ≥ 70 / Low < 70.
  • An unmeasured zone is not "Low", and a zone with no rider-days must not drag the target down.
  • Off Structure (contracted OFF days, default 2) driving Required Hours = (month days − OFF) × full-day hours, with a per-rider editor and a bulk Excel upload.
  • An Excel-like grid: block selection, fill, copy / paste, and one reason for a whole batch, recorded in an audit trail.
  • A rule simulator so Ops can see the outcome of a hypothetical day without saving.
  • All of it editable by staff without a code release.

5. Gold table C — zone efficiency arithmetic

ZoneOrdersRider-daysDPDEfficiencyBand (110 / 70)
A1,2004030.00130.4%Good
B4002516.0069.6%Low
C00——Not set
  1. Target DPD = (30.00 + 16.00) ÷ 2 = 23.00. Zone C is excluded because it has no rider-days.
  2. Zone A = 30 ÷ 23 × 100 = 130.4% → Good.
  3. Zone B = 16 ÷ 23 × 100 = 69.6% → Low. Note it is below 70 — a 70.0 boundary reading must be Average, a 69.6 must be Low.
  4. Fail case: if Zone C had been counted as 0, the target would be 15.33 and Zone B would read 104.3% → Average. If you see Average for Zone B, the empty zone is being counted.
  5. Set the override for Zone B to Good, recompute, and Zone B must stay Good with an Edited tag and the automatic band still visible beside it.
  6. Change the client's thresholds to Good ≥ 105 / Average ≥ 60: Zone A stays Good, Zone B becomes Average (69.6 ≥ 60).
  7. A zone with a 0 rider-day month must never show 0.00 DPD — it shows an em dash and Not set.

13. Verify — User (rider app inputs)

There is no rider-facing payroll screen in this release and no rider app build to install. Payroll v4 is admin-only. What is tested here is that the three rider-side inputs land correctly on the admin grid. Any tester filing "the app has no payroll page" is filing the wrong ticket.

  1. Clock-in hours: an open attendance log (clocked in, not yet out) must credit 0 h for that day, not a running total.
  2. A clock-out before the shift start must not add the pre-shift gap.
  3. Orders: an in transit or pending order must not raise the day's orders — only a verified order counts toward the rule.
  4. Requests: only an Approved Leave / Sick / Accident / Vehicle request covers a day. Pending and Under review leave the day unjustified.
  5. Arabic locale: the rider sees the ordinary request flow in Arabic; nothing new appears in the app.

14. Regression guardrails — the four that must never break

  1. A client with no saved rules changes nothing. Its month must be byte-identical to the pre-v4 classification: clocked-in = 12 h, covered = the cover, otherwise Absent.
  2. Operations beats a rule. An approved Sick day must be Sick · 0 h even when the rule list would have said Full day.
  3. A manual adjustment beats Operations. Adjusting an approved Sick day to Full day produces Full day, with the marker and the reason recorded.
  4. A recalculation never overwrites an adjustment. Recompute the month and every hand-adjusted cell keeps its manual value.
